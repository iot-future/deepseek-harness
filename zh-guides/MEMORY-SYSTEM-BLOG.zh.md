# DeepSeek Harness 记忆系统漫游指南：一本永不失忆的账本，一扇可调节的观察窗

> 这不是一篇 API 文档，而是一趟**从问题出发**的旅程。
>
> 我们将扮演一个"想给 agent 装上记忆"的工程师。先看看业界通用的做法长什么样、它有哪些让人睡不着觉的痛点，再亲眼看着 DeepSeek Harness（以下简称 dsh）的设计者如何针对每一个痛点，给出反直觉却自洽的答案。每个答案，都在揭示更深一层的设计哲学。

---

## 第一步：先看看"通用做法"长什么样

几乎所有主流 agent 框架，记忆架构都长这样：

| 记忆层 | 通用做法 | 存在哪 |
|---|---|---|
| 短期记忆（本轮对话） | 一个**消息数组**，每轮对话往里 push 一条 | 内存 |
| 长期记忆（跨会话） | 向量数据库 / 摘要文件 / 会话记录表 | 外部存储 |
| 全局记忆（跨项目） | 用户画像库、偏好表 | 外部存储 |

关键在短期记忆那一行：它其实只有**一份可变的消息数组**——模型看到的对话历史存在哪，它就在哪。交互发生时，系统会顺手发一条事件"通知"出去（告诉其他模块"刚才发生了这事"），但这通知**发完即弃，不做任何留存**。

于是整个行业在为这个结构默默买单：

1. **历史只在数组里**——数组之外无痕，"发生过什么"的完整流水账根本不存在；
2. **删除即真删**——上下文太长时，通用做法是直接把早期消息从数组里删掉，删完历史就真的没了；
3. **通知不留痕**——事件发完就丢，事后想审计"当时发生了什么、谁改了什么"，无从谈起。

带着这三个痛点（**历史不完整、删除即丢失、不可审计**），我们来看 dsh。而 dsh 的第一个答案就让你愣住：

> **dsh 里没有一张 memory 表、没有一个 memory 模块。**

所谓"记忆"，是设计者对"一个 agent 的完整历史如何被记录、重建、压缩、恢复"这个问题的系统回答。下面六个问题，每个都先问"通用做法怎么做、痛在哪"，再看"dsh 怎么答"。

---

## 问题一：会话历史怎么存？（需求：记住发生过什么）

### 通用做法与它的痛

通用做法就是刚才说的：**一份可变的消息数组 + 事件仅作通知**。交互发生时，往数组里塞一条消息，同时发一条事件通知给其他模块——然后通知就没了。它的痛我们已经看到了：历史只在数组里，删了就真没了，通知不留痕。

### dsh 的答案：把"通知"升级为"状态"

dsh 没有去补一份事件流水（那是又造一份要同步的东西），它做了一个更根本的升级——**让这条"发完即弃的通知"变成唯一且持久的状态**：

> **日志是唯一的事实来源（single source of truth）。一切能从这个来源派生出来的东西，都不单独存储；一切能被日志解释的东西，才允许进入模型视野。**

每一次交互（用户消息、AI 回复、工具结果）都作为**不可变事件**，追加进一条只增不减的日志。**日志就是状态**——消息数组？那是从日志里"算"出来的，不是存出来的。同一个日志，对系统是"事件记录"，对模型是"对话历史"：一个东西，扮演两个角色。

这带来一个结构性保证，而不是"测试保证"：

> 「采用事件溯源后，日志本身即是状态，**分歧在结构上不可能发生**。」

这句话值得停下来想：它不是"我们写了很多测试防止漂移"，而是"漂移这件事在结构上根本无从表达"——因为根本不存在"另一份"可以漂移的东西。一个 bug 类别，被彻底消灭了。

| 对比 | 通用做法（消息数组） | dsh（事件日志） |
|---|---|---|
| 状态存哪 | 一份可变消息数组 | 一份只追加事件日志 |
| 事件是什么 | 发完即弃的通知 | **日志本身就是状态** |
| 完整历史 | 不存在（数组之外无痕） | 永远完整，永不丢失 |
| 回放 / 追踪 / fork | 各自写一套 | 都是日志的免费赠品 |

### 免费的赠品

因为日志完整且唯一，三个能力白送：**回放**（fork / resume / replay 时，新会话 = 从旧日志前缀重放；普通新会话从空日志开始）、**追踪**（遥测不用埋点，就是日志的另一个读者）、**fork**（复制一段日志前缀，天然无遗漏）。

### 第一枚心智烙印

> 遇到"记录"和"状态"要分成两份维护的困境时，解法永远不是"再加一个同步机制"，而是"**让一个东西同时扮演两个角色**"——把易失的通知升级为持久的状态，分歧在结构上不可能。这个思想后面还会反复出现。

## 问题二：历史越来越长怎么办？（需求：上下文有界）

### 通用做法与它的痛

通用做法是**截断或删除**：滑动窗口，太长的旧消息直接扔掉；或者用摘要替换——但那是"**改写历史**"：把数组里那一段直接换成摘要。它的痛有三个：

1. **丢了就真丢了**——旧消息删掉后，想找回来说不清；
2. **不可审计**——不记录"这次改写用掉了哪些事件"，回放时没法核对；
3. **顺序敏感**——多个插件都来改历史，谁先改谁后改，结果不同且不可控。

### dsh 的答案：surface——事实与观点分离

先看它怎么解决"改写"的问题。dsh 引入了一个派生层 **surface（有序表面）**：模型看到的，不是日志本身，而是从日志投影出来的 surface。

把系统比作一间办公室：

| 东西 | 比喻 | 规则 |
|---|---|---|
| 事件日志 | 流水账本 | 只往后写，绝不撕页、绝不改写 |
| surface | 墙上的白板 | 决定模型此刻看到什么，可以随便换纸条 |
| 投影 | 抄写员 | 账本记了什么，白板就跟着更新 |

抄写员只有两个动作：

1. **贴新纸条**（append）：账本新增一条对话 → 白板末尾贴一张纸条；
2. **换纸条**（replace）：白板太满 → 揭下中间一段旧纸条，贴上一张摘要纸条。**被揭掉的纸条在账本里原封不动。**

于是有了这句贯穿全文的话：

> **日志 = 事实（真相），surface = 观点（读模型）。压缩改的是观点，不是事实。**

对比通用做法，差异是根本性的：

| 对比 | 通用做法 | dsh |
|---|---|---|
| 压缩的本质 | **改写事实**（删除 / 替换消息） | **改写观点**（投影层换纸条） |
| 删掉的历史 | 真的没了 | 永远在账本里，随时可重新记起 |
| 可审计性 | 说不清改了哪些 | 每次 replace 记录被顶替的事件 seq，回放可核对 |
| 结构 | 核心 `deriveMessages` 频繁改动 | 新机制都走同一套投影，核心不动 |

另外，超大的工具输出还有第二道闸门——**spill 落盘**：在事件**写入日志之前**，大文本就写进文件，日志里只存一个定位符 + 首尾预览。它不是 surface 操作（不换纸条、不 shadow 节点），而是让 tool/result 事件在入账时就更瘦。这样连"单条事件的体积"都控制住了。日志无限增长带来的只有廉价的存储成本（磁盘上追加 JSONL/SQLite 很便宜），**模型成本（token）却被牢牢焊死在有界窗口里**。

### 第二枚心智烙印

> 改动"事实"是危险的，改动"观点"是安全的。设计者把所有需要"改"的东西都赶到"观点"这一侧，让"事实"永远只追加、不可变。

## 问题三：投影怎么知道谁重要？（需求：谁进模型视野）

### 通用做法与它的痛

通用做法里，"什么该给模型看"通常靠**检索或打分**：向量相似度检索、重要性启发式、相关性排序——一套"智能判断"。它的痛是：判断逻辑黑盒、随状态变化、不可预测也不可审计。"模型为什么没看到那条？"只能回答"相似度不够高"。

### dsh 的答案：它不判断

这是整套设计里最反直觉的一点——**投影函数是个不看内容、只看标签的死脑筋**。重要不重要，早在事件写进日志的那一刻就定好了。

两道筛选，全都发生在**写日志时**：

1. **类型门槛（硬规则）**：只有三种事件有资格上白板——用户消息、AI 消息、工具结果。其余（分片、工具调用记录、压缩起止标记……）都是"过程记录"，仅供回放、追踪、审计，模型永远看不到。
2. **自报标记（声明式）**：够格的事件必须自带标签 `surfaceOp`——"我是追加（append）"还是"我顶替谁（replace [start, end]）"。**不带标签的够格事件会被拒绝写入**，防止有人悄悄漏掉。

判断者不是投影函数，而是**发出事件的模块**：

| 谁在判断 | 判断什么 |
|---|---|
| agent 循环 | 对话消息必须给模型看，标 `append` |
| 压缩插件 | 白板太满，挑一段旧内容浓缩成摘要，声明 `replace [start, end]` |
| 落盘策略（spill） | 单条结果太大，留预览、全文挪走——这是**入账前的内容改写**（post-execute 变换），不是 surface 操作 |

### 为什么不能让它自己"聪明地判断"？

| 对比 | 通用做法（检索/打分） | dsh（声明式标签） |
|---|---|---|
| 判断时机 | 读取时（投影函数现场算） | 写入时（生产者贴标签） |
| 可预测性 | 随状态变化 | 同样的日志永远同样的结果 |
| 可审计性 | "相似度不够" | "写日志的人声明了不贴"，账目清楚 |
| 职责归属 | 混杂在通用函数里 | 各模块各管各的判断 |

你可能觉得：让函数看看内容、打打分不是更智能吗？但那样会毁掉最值钱的三样东西：**不可预测**（同样的日志投影出不同的白板，缓存稳定直接崩塌）、**不可审计**、**职责混乱**（重要性是业务决策，不该埋进通用投影函数）。

### 第三枚心智烙印

> 一个不需要动脑的执行器，就永远不会"想错"。判断留给各模块，投影只照章办事。

## 问题四：凭什么是"纯函数"投影？（需求：可重建 + 缓存稳定）

### 通用做法与它的痛

模型服务的缓存认"请求前缀"，前缀变了缓存就失效。通用做法是：**专门设计一套缓存管理逻辑**，小心翼翼地维护前缀稳定——这是把"缓存"当成一个要管理的对象，往往越管越复杂。

### dsh 的答案：先立铁律，再谈性能

dsh 先立了一条铁律：

> **模型可见 ⟺ 已记录**（Model-visible means logged）。凡到达模型请求的内容，都必须能从日志（及其引用的不可变对象）重建出来。

然后指出一个惊人的结论：

> 「一个**仅追加**的日志，经**逐节点的纯函数投影**，在 header 不变时，自然产出前一请求的**追加扩展**——稳定性是**涌现的，不是管理出来的**。」

翻译成人话：账本只往后写 + 抄写员规则死板 + 每次只处理新增部分 → 这次白板上的内容，必然等于上次白板的内容**后面再接一小段新的**。前缀稳定不是代码刻意维护的，是"只追加 + 纯函数"这两个约束自动长出来的。**缓存命中是白送的福利，不是目标。**

| 对比 | 通用做法 | dsh |
|---|---|---|
| 缓存稳定的来源 | 专门的缓存管理代码 | "只追加 + 纯函数"约束的推论 |
| 正确性 vs 性能 | 性能优先，正确性靠测试 | 正确性优先，性能自己跟上 |

### 投影具体怎么做：折叠 + 派生

第一步是**折叠（fold）**——把日志"读成"白板上的纸条列表。实现上只是两种数组操作：

```
事件序列（seq 0~6）                        surface 节点数组（纸条列表）
─────────────────────────────────────────────────────────────────
seq0  user/message      append         [0]
seq1  assistant/message append         [0, 1]
seq2  tool/call         无标记（跳过）   [0, 1]
seq3  tool/result       append         [0, 1, 3]
seq4  压缩摘要（user/message） replace [0..3]  [4]
seq5  user/message      append         [4, 5]
seq6  assistant/message append         [4, 5, 6]
```

- `append` → 数组末尾 `push`；
- `replace [start, end]` → 定位两个端点在数组里的位置，`splice` 掉整个闭区间，插入自己的 seq。

**"逐节点"的奥义在增量**：抄写员记住上次处理到的位置，下次只处理新增部分——没有新事件时 O(1)，有新事件时 O(新增数)，绝不全量重扫。日志再长，投影只跟随尾部。

第二步是**派生（derive）**——把纸条逐张翻译成模型认识的对话格式：

| 纸条 | 翻译结果 |
|---|---|
| 用户消息 | 原样作为 user 消息 |
| AI 消息 | 取出内部消息（内容为空的跳过，它只承载用量统计） |
| 工具结果 | 取出内部消息 |
| 其他 | 不翻译（null），不进模型 |

### 怎么保证"日志重建的"和"运行时看到的"一致？

两套实现共享同一套折叠规则：`foldSurface`（全量回放，用于重建/审计）和 `SurfaceManager`（增量运行，用于实时投影）。再加上**提交前校验**（seq 连续、标记合法、`sourceEventSeqs` 必须覆盖每一个被顶替的节点、工具结果替换只允许改内容）——所以日志里重建出来的，和运行时刻的，必然逐字节一致。这就是"一个日志无法解释的请求，不可能被意外构造出来"的硬保证。

### 第四枚心智烙印

> 不要用"管理"去对抗"漂移"，要用"结构约束"让"漂移"无从发生。正确性放在第一位，性能只是顺带的福利——而当正确性做到位，性能反而自己跟上了。

## 问题五：项目与项目之间能隔开吗？（需求：记忆隔离）

### 通用做法与它的痛

通用做法是把记忆"分区"：向量库按 namespace 分、文件按文件夹分。但它有两个问题：**分区是逻辑约定，不是结构保证**（一个错误的检索参数就能串库）；**隔离靠权限检查**，默认往往是"能看"，要额外配置才"不能看"。

### dsh 的答案：默认就是隔开的

不是"可以配置隔离"，是"不加任何配置就互相看不见"。三层隔离：

**第一层，物理单元：会话。** 每个会话一本独立账本（独立日志文件、独立 surface、独立 spill 目录）。模型在某个会话里干活，天然只能看到这本账本——别的账本根本不碰。这是结构决定的，不是权限检查拦下来的。

**第二层，项目维度：cwd 门牌号。** 每个会话自带"门牌号"（cwd，它在哪个工作目录启动）。跨会话的**工具访问**要求门牌号严格相等——项目 A 和项目 B 天然两个世界。注意这条铁律只管工具通道：点名（mention）是显式特例，门牌号只影响候选排序，不决定能否点名。

**第三层，显式通道：点名 + 限额。** 隔离不是禁止交流，而是交流必须显式、可审计、有限额：

| 通道 | 规则 |
|---|---|
| 会话引用（mention） | 模型显式 `@[标题](dsh-session:...)` 点名另一个会话，系统做成**只读快照**注入；一次最多 3 个源、单个 64KB、禁止自引用、**是快照不是实时链接** |
| 会话查询工具 | `session_search` 等工具**默认不挂载**（opt-in），挂载后必须过 cwd 相等授权 |

| 对比 | 通用做法 | dsh |
|---|---|---|
| 隔离性质 | 逻辑分区（约定） | 物理独立（结构） |
| 默认值 | 默认可访问，配置才隔离 | **默认隔离，点名才互通** |
| 跨项目访问 | 检索参数 / 权限 | 工具严格相等 + 点名显式通道 + 限额 |

用档案室的话说：**每个项目一间档案室，每本账本一个抽屉，全部默认上锁。隔开是默认，互通是特例。**

## 问题六：跨对话的用户画像怎么记？（需求：全局记忆）

### 通用做法与它的痛

通用做法是建一张**用户画像表 / 向量记忆库**：一个全局的"画像存储"，所有会话读写。它的痛在于：**全局存储和会话日志是两份东西**（又回到了问题一的漂移），而且**写入不可审计**——画像被改了，说不清是谁、在什么上下文里改的。

### dsh 的答案：没有内置模块，但有三条路

dsh 里没有内置"用户画像"模块——它的哲学决定了会话日志才是事实源，全局画像属于"空白地带"。但有两块现成的地基可以借用：

| 现成机制 | 干什么的 | 对画像有什么用 |
|---|---|---|
| identity（匿名用户 ID） | 跨会话识别"是同一个用户" | 画像的**主键**——没有它，画像不知道归给谁 |
| settings（用户设置） | 用户级、跨会话的持久化文档，带 schema 校验 | 画像**存储容器**的成熟模板 |

要真正落地，有三条路，丰俭由人：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 画像会话**（零代码） | 给每个用户开一个专属会话，画像更新 = 追加事件；其他会话用 mention 显式引用 | 完全符合"日志即事实源"，天然可审计、可回放 | 模型得"记得"去引用；快照有 64KB/3 源上限 |
| **B. 文件注入**（最轻） | 画像存成文件，会话启动时自动注入 system prompt | 任何会话自动加载，实现简单 | **写入不可审计**，绕开了"模型可见 ⟺ 已记录"铁律 |
| **C. 自建 seam**（工程化） | 照抄 settings 模式注册 `ctx.userProfile` 服务，JSONL 后端 + schema 校验 + 注入 + 审计事件 | 可替换后端、可校验、产品级 | 要写插件代码 |

注意这三条路和通用做法的根本差异：即使选 C（最接近"画像表"的路），dsh 也坚持**每次画像更新 = 追加一条可审计事件**，而不是直接改一张表——因为这套系统的底线始终是：

> **任何影响模型的东西，都得能说清楚它是怎么来的。**

---

## 收尾：六个问题，一套与通用做法不同的心智模型

回头看，六个问题的答案串起来，是一套高度一致的对比逻辑：**通用做法在"管理"复杂度，dsh 在"消灭"复杂度。**

| 问题 | 通用做法 | dsh 的做法 | dsh 的特色思考 |
|---|---|---|---|
| 历史怎么存？ | 消息数组（事件仅作通知） | 事件溯源，日志即状态 | 通知升级为状态，分歧在结构上不可能 |
| 历史太长怎么办？ | 截断 / 改写历史 | surface 投影 + 压缩 | 事实与观点分离，改观点不改事实 |
| 谁进模型视野？ | 检索 / 重要性打分 | 类型门槛 + 自报标记 | 判断发生在写入时，投影不思考 |
| 凭什么是纯函数？ | 专门的缓存管理 | 折叠 + 派生 + 提交前校验 | 结构约束让缓存稳定涌现 |
| 项目间怎么隔开？ | 逻辑分区 + 权限检查 | 会话物理隔离 + cwd + 显式通道 | 隔开是默认，互通是特例 |
| 全局画像怎么办？ | 全局画像表 | 画像会话 / 文件注入 / 自建 seam | 全局记忆也要守住"可审计"底线 |

如果只看机制，会觉得 dsh 是"功能越多越好"的加法思维；恰恰相反，它最鲜明的性格是**极致的克制**——能派生的绝不存两份，一种表示绝不做两套，一个锁绝不做两个。它的底色，可以用设计者自己的两句话收束：

> 「分歧在结构上不可能发生。」
> 「稳定性是涌现的，不是管理出来的。」

前者定义了**可靠性**的边界——把错误挡在结构之外；后者定义了**优雅**的边界——好的性质是约束的自然产物，而不是额外代码维护出来的。dsh 的记忆系统，就是这两句话在一个真实工程里的完整展开。

以及贯穿全程的那副图景：**一本永不失忆的账本，一扇可调节的观察窗。** 记忆只有一层（日志），遗忘只是把窗户调窄，账本一个字都不少。
