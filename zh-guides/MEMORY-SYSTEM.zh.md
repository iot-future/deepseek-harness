# DeepSeek Harness 记忆系统的设计思想

> 这不是一份 API 说明，而是一份**设计哲学**文档：回答「设计者为什么这么设计」「拒绝了哪些方案」「背后是一套怎样的思想」。
>
> 阅读前提：先放下「记忆」这个词的直觉。dsh 里没有一张 memory 表、没有一个 memory 模块。所谓「记忆」，本质上是设计者对「**一个 agent 的完整历史如何被记录、重建、压缩、恢复**」这个问题的系统回答。

---

## 一、总纲：一条原则贯穿一切

整套记忆系统，可以收敛成一句话：

> **日志是唯一的事实来源（single source of truth）。一切能从这个来源派生出来的东西，都不单独存储；一切能被日志解释的东西，才允许进入模型视野。**

这句话拆成两条腿：

1. **记录侧**：agent 的全部交互，被追加成一条不可变的、只追加的事件日志。日志**就是**状态，不另设一份状态。
2. **读取侧**：模型看到的历史，是从日志**派生**出来的，从不单独存一份。

理解了这条总纲，后面的每一个机制——surface、压缩、spill、持久化、检索——都只是它在不同场景下的自然推论。

> Java 对照：这就是 **Event Sourcing（事件溯源）+ CQRS 投影** 的彻底形态。Event Store（事件日志）是唯一真源，Read Model（surface / deriveMessages）从它投影。但 dsh 把它推到了一个 Java 项目里很少见到的极致——下面会看到。

## 二、五个根本决策，以及它们背后的「为什么」

### 决策 1：事件溯源——让「分歧」在结构上不可能

设计者最初面对一个选择题：会话历史怎么存？

- 方案 A（被否决）：**可变的消息数组** + 事件仅作为通知发出。简单，但「状态」和「日志」是两份东西，迟早会漂移、会分歧。
- 方案 B（采纳）：**事件溯源**。日志即状态。

设计者给出的采纳理由是全文最重的一句话：

> 「采用事件溯源后，日志本身即是状态，**分歧在结构上不可能发生**。」

这句话值得停下来想。它不是一个性能决策，也不是一个功能决策，而是一个**可靠性决策**。设计者要的不是「通过测试保证不漂移」，而是「通过结构设计，让漂移这件事根本无从表达」——一个 bug 类别的彻底消除。

由此带来三个「结构上得到保证」而非「事后附加」的能力：

- **回放**：用已有日志初始化一个新会话，就是回放。因为日志是完整的，回放天然完整。
- **追踪 / 遥测**：追踪不是额外埋点，而是日志的另一个读者。
- **fork**：fork 一份会话 = 拷贝一段日志前缀，天然无遗漏。

> 这是这份设计的第一个心智烙印：**遇到「两份东西要保持同步」的困境时，设计者的解法永远不是「加一个同步机制」，而是「消灭其中一份」**。这个思想后面还会反复出现。

### 决策 2：surface——把「改写历史」变成「可审计的投影操作」

事件溯源有个经典难题：历史是只追加、不可变的，但如果上下文太长，agent 必须「忘掉」一部分早期历史，怎么办？

naive 的解法（被否决）是：让压缩插件直接改写派生出来的请求。但这有三个致命伤：

1. **监听器顺序脆弱**：谁先改、谁后改，结果不同，且不可控。
2. **无法审计**：不记录「这次替换用掉了哪些事件」。
3. **核心被迫频繁修改**：每新增一种「改写历史」的方式，都要去改 `deriveMessages()`。

设计者的解法，是引入一个专门的**投影层——surface（有序表面）**：

- surface 是「**会产生模型消息的事件**」的有序子集（三种：`user/message`、`assistant/message`、`tool/result`）。
- 每个消息事件，都必须声明它**如何进入 surface**：要么 `append`（正常追加），要么 `replace [start, end]`（用本节点顶替一段位置）。
- 被 `replace` 掉的事件**仍然留在日志里**，只是不再投影进模型历史。

这里藏着一个非常漂亮的对称性，是理解整个设计的关键：

> **日志 = 事实（真相），surface = 观点（读模型）。压缩改的是观点，不是事实。**

你可以「忘掉」一段历史（从 surface 上拿掉它），但那段历史永远还在日志里，随时可以重新记起。这与 Event Sourcing 里的「快照（Snapshot）」完全同构——快照加速读，但永不丢弃历史。

而 `sourceEventSeqs` 这个字段，让「改写」变成了「可审计」：每次 replace 都记录「我顶替掉了哪些事件的 seq」，于是**回放时可以验证：这次替换确实列出了它移除的每一个事件**。改写不再是一个黑盒操作，而是一条可核对的账目。

> 第二个心智烙印：**改动「事实」是危险的，改动「观点」是安全的。设计者的做法是把所有需要「改」的东西，都赶到「观点」这一侧去做，让「事实」永远保持只追加、不可变。**

### 决策 3：可重建性铁律——「缓存稳定」是涌现的，不是管理的

这是整套设计里**最深刻**的一处，也最容易被表面机制掩盖。

先看问题：agent 的请求流水线里，模型调用希望命中**提供方的 KV 缓存**——即前一次请求的 prefix 能被下一次复用，省 token。但「每次请求都从零重新拼装消息」会让 prefix 不稳定，缓存失效。

很多系统的做法是：**专门设计一套缓存管理逻辑**，小心翼翼地维护 prefix 稳定。

dsh 设计者的做法完全不同。他先立了一条铁律：

> **模型可见 ⟺ 已持久引用**（Model-visible means logged）。
>
> 凡到达模型请求的内容，都必须能从日志（及其引用的不可变对象）重建出来。

然后，他指出了一个惊人的结论——**缓存稳定性根本不需要「管理」，它是这条铁律的免费推论**：

> 「一个**仅追加**的日志，经**逐节点的纯函数投影**，在 header 不变时，自然产出前一请求的**追加扩展**——稳定性是**涌现的，不是管理出来的**。」

翻译成人话：因为日志只追加、投影是纯函数（同样的输入永远给同样的输出）、且请求头没变，所以第 N 次请求的消息，必然是第 N-1 次请求消息的「前缀 + 新增尾巴」。前缀稳定不是靠代码刻意维护，而是**从「只追加 + 纯函数」这两个约束里自动涌现出来的**。

于是设计者得到了三个「免费」的推论，按重要性排序：

1. 前缀缓存稳定（推论 #1）
2. 逐字节精确的审计与回放（推论 #2）
3. 带可归因漂移的恢复与 fork（推论 #3）

**注意这里的价值观：他把「正确性」（可重建、可审计）放在第一位，「性能」（缓存命中）只是顺带的福利。** 这是「先保证正确，再谈优化」的典型体现——而且他发现，当你把正确性做到位，性能反而自己跟上了。

配套的执行手段是「**独立重建校验**」：用一个全新的 Session 独立重建每个请求，跟实际发出的请求比对，一旦不一致就说明日志缺失了信息。这保证了一个硬性结论——**一个日志无法解释的请求，不可能被意外构造出来**（变异已构建的请求会直接抛异常）。

> 第三个心智烙印：**不要用「管理」去对抗「漂移」，要用「结构约束」让「漂移」无从发生。** 缓存稳定、审计可回放、恢复可归因，都不是写出来的功能，而是「只追加日志 + 纯函数投影」这两个约束的自然产物。

### 决策 4：拒绝而非猜测——fail loud 的彻底贯彻

记忆系统要面对「读到一份自己不认识的数据」的场景。这里设计者做了一个在数据库领域颇受争议、但极其一致的选择：

**永远拒绝，绝不猜测。**

体现在三个层次：

1. **格式版本不匹配 → 拒绝**。读到比当前更新的版本，报「由更新的 harness 写入，请升级」，并给出原始日志文件路径（用户仍能看到原文）；读到更旧的版本，只在内存里走「升级器链」转换，且只在真正继续时才落盘。**宁可让用户升级，也不读错。**

2. **未知事件类型 → 拒绝**。读到不认识的事件，拒绝解读整个会话，除非该事件信封上显式标注了 `ignorable: true`。而且**默认是「必需」**，不是「可忽略」——设计者原话是：

   > 忘写 `ignorable` 标记的后果，是把一个本可恢复的会话拒绝过头（体验问题）；而默认可忽略，会让同样的疏忽**静默恢复出一个残缺的会话（安全事故）**。

   两害相权，他坚定地选择了「宁可误拒，不可误读」。

3. **崩溃孤儿 → 变成「可检测」**。压缩进行到一半崩溃，会留下一个没有配对的 `compaction/start`。设计者不试图「修复」它，而是让它成为**一个可被明确检测到的孤儿标记**——「把崩溃窗口从*静默损坏*转变为*可检测的孤儿*」。

> 第四个心智烙印：**「静默地错」是比「显式地失败」更严重的失败。** 这一整套设计反复在做同一件事——把所有「可能悄悄出错」的地方，改造成「要么正确，要么响亮地拒绝」。

### 决策 5：日志即锁——用持久化事件做并发控制

压缩是个慢操作（要调一次模型）。两个压缩同时发生会互相踩踏。常规做法是加一个进程内 mutex。

设计者没有引入 mutex，而是**让日志里的一对事件本身充当锁**：

- `compaction/start` 追加时「上锁」；
- `compaction/end` 追加时「解锁」；
- 任何新的压缩入口看到「有 start 没 end」，就直接拒绝（busy）。

这个选择的精妙之处在于：**锁的状态不是一份独立的、易失的内存状态，而是持久日志的一部分**。于是：

- **崩溃后锁的状态依然可判定**：崩溃留下「孤立的 start」，后来者一眼就能看出「这里死过一次压缩」。
- **跨进程 / 跨生命周期依然正确**：日志里新写入的 `session/end-seed` 标记，天然区分「这条 start 是上一个生命周期的死锁」还是「当前生命周期的活锁」。

同样的思想还体现在别处——「用日志记录的事实，代替任何进程内的易失状态」。因为日志是唯一真源，所以凡是需要「记住」的状态，记进日志就自动获得了持久性和崩溃安全性。

> 第五个心智烙印：**不要为「需要持久的状态」单独发明一份易失的内存副本。** 既然日志是唯一真源，那么「锁」「边界」「进度」这类状态，直接写成日志事件，就同时解决了「并发」和「崩溃恢复」两个问题。

## 三、贯穿始终的审美：宁可少，不可多

如果只读机制，会以为设计者是「功能越多越好」的加法思维。恰恰相反，这份代码库最鲜明的性格是**极致的克制**。有一个决策最能说明问题——**删除可变的会话摘要（SessionSummary）**。

背景：最初设计了一个「可变摘要」，想在日志之外，单独维护一份 `title` / `firstPrompt` / `updatedAt`，用于未来的「会话列表」界面（按最近排序、显示标题预览）。

结果审计发现：这套东西**从未被任何人读取**——标题来自持久化的 `session/title` 事件，排序和预览都能从日志直接派生，唯一「不可派生」的用户手动编辑标题功能又从未实现。

于是设计者做了决定：**彻底删掉它**。理由是全文最戳人的一句：

> 为一个尚不存在的功能维护缓存，是每个后端都要承担维护成本、每个约定测试都要承担断言成本的无谓负担。

而这次删除沉淀出一条方法论，被写进了根 AGENTS.md：

> **通过的测试固定的只是「当前行为」，不一定是「正确行为」；行为可能是过去妥协的产物。**

这句话的分量在于：它提醒每一个后来者，**不要因为「现在跑得通」就以为「现在是对的」**。当某个设计可以被更简单的东西取代时，要有勇气把它删掉。

这条「宁可少，不可多」的审美，在整个记忆系统里无处不在：

- 能派生的，绝不存两份（标题、预览、排序、消息历史……全部从日志派生）。
- 一种表示，绝不做两套（`request/header` 用完整快照，拒绝 delta 编解码器——「只保留一种回放表示」）。
- 一个职责，绝不混进另一个 seam（测量归 token-meter，摘要归 compaction，预览归 retention，存储归 spill——互相独立）。
- 一个锁，绝不做两个（`compaction/start…end` 事件对就是锁，没有进程内 mutex 重复承担同一职责）。

> 第六个心智烙印：**简单不是「写得更少」，而是「不存在的状态更少」。** 每多一份需要维护的状态，就多一份漂移的可能、多一份测试的负担。设计的最高境界，是让大部分状态「根本不需要存在」，因为它们随时可从唯一真源派生。

## 四、几个反直觉的取舍，暴露设计者的品味

有几个看似「奇怪」的决定，恰恰最能体现这套设计的品味：

**1. 压缩摘要居然是一条 `user/message`，而不是专门的 `compaction` 事件。**

直觉上，「一段历史的摘要」应该是个特殊的东西。但设计者说：`SurfaceEventType` 是封闭的（只有三种消息事件能进 surface），而摘要确实**就是** user 角色的上下文——模型看到它，就应该把它当作用户说的一段话。所以「复用 `user/message` 是诚实的，而非变通」。`compaction/*` 事件只记录簿记（锁、范围、token 数），不进 surface。

**2. 核心会话修复对「压缩」完全无感知——这是故意的。**

崩溃恢复代码（`interruptedTurnClosers`）从不被教导「认识 `compaction/*`」。设计者的理由：如果每新增一种 `xxx/start…end` 事件对，都要去改核心修复代码，那正是「能力 seam 架构存在的意义所要避免的耦合」。通用机制（`session/end-seed` 生命周期边界）已经提供了区分「死锁」和「活锁」的证据，压缩自己负责解释它。

**3. 完整快照，而非增量编码。**

`request/header` 每次都写完整快照，而不是 delta。看似浪费字节，但设计者愿意为「只保留一种回放表示」付这个代价——delta 编解码器会复制一套表示 + diff/apply/fallback 机制，那是另一种形式的「两份东西要保持同步」。

**4. 工具结果裁剪（pruner）和压缩，本质是同一件事。**

裁剪一个超大的 `tool/result`，本质就是一次 `replace`（`start === end` 的单节点替换）——它「属压缩家族」。设计者不为其发明新机制，而是复用同一套 surface 投影。

这些取舍的共同指向：**当一个「新问题」出现时，先问它是不是某个已有机制的「特例」。如果是，就复用；绝不为每一个表象各发明一套机制。**

## 五、把「记忆」拆成能力 seam：单一职责的极致

记忆系统的每一个「环节」，都被拆成了一个独立的**能力 seam**（接口 + 实现 + 消费方），而不是一个臃肿的大模块：

| 关注点 | 归属 | 它只负责 |
|---|---|---|
| 测量 token | `token-meter` | 回放感知的估算，别的不管 |
| 生成摘要 | `compaction` | 决定「压什么、产出什么摘要」 |
| 裁剪工具结果 | `tool-result-pruner` | 只做「删中间、留头尾」 |
| 预览大文本 | `output-retention` | 只做「保留哪部分、省略了什么」 |
| 落盘大文本 | `spill` | 只做「保存文本，返回定位符」 |
| 持久化日志 | `session-persistence` | 只做「把事件写进 JSONL/SQLite」 |
| 检索历史 | `session-query` | 只做「授权读取和搜索」 |

而且，**接口只声明「做什么」，算法全部留在后端实现**。压缩接口暴露的是 `compactIfNeeded` / `compactNow` / `compactRegion` 三个抽象方法，而「保留遍历、token 求和、文本提取」这些「怎么做」的决策，全部沉到 `compaction-basic` 后端里。设计者的理由一针见血：

> 把完整算法作为接口上的具体方法，会把约定重新耦合到一种策略：想要不同保留策略的后端，必须与继承来的具体代码对抗。

这意味着：**换一个压缩策略，等于换一个后端插件，接口一行不改**。这正是整个 dsh「一切皆插件」架构在记忆系统上的落地——记忆的每一个环节都可替换。

## 六、总结：这套设计背后的心智模型

把上面所有决策连起来，可以看到一个高度一致的心智模型：

1. **一个真源**：只追加的事件日志，是唯一事实来源。
2. **一切皆派生**：能派生的不存储，存储的只有一个真源。
3. **事实与观点分离**：日志（事实）不可变，surface（观点）可被 `replace` 改写——压缩改的是观点，事实永不丢失。
4. **正确优先于性能**：先保证「模型可见 ⟺ 可重建」，缓存稳定是它的免费推论，而非刻意追求的目标。
5. **拒绝而非猜测**：读不懂就响亮地拒绝，绝不静默地读错。
6. **结构消除错误**：不靠测试/检查去「发现」漂移，而靠结构设计让漂移「无从表达」。
7. **日志即状态**：锁、边界、进度，直接写成日志事件，同时解决并发与崩溃恢复。
8. **极致克制**：宁可少，不可多；不为不存在的功能维护状态；一种表示，绝不做两套。
9. **能力 seam 化**：每个环节是「接口声明做什么 + 后端决定怎么做」，可独立替换。

这套思想的底色，可以借设计者自己的两句话收束：

> 「分歧在结构上不可能发生。」
> 「稳定性是涌现的，不是管理出来的。」
